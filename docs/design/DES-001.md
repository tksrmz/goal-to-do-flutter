# Goal to Do MVP 設計書（データ設計・アプリ構成）

- 作成日: 2026-11-07
- 要件: [REQ-001](../spec/REQ-001.md)
- ステータス: ドラフト

## 1. 前提

設計判断の前提とする、要件から読み取れる性質。

| 性質 | 根拠 | 設計への影響 |
|------|------|-------------|
| シングルユーザーで、データ量は小さい | REQ-001 2章 | 書き込み頻度は人の操作の速さ（1秒に数回）が上限で、ホットスポットやスループットの心配はない |
| 3層のツリーで、親の付け替えがある | 原理1、6.3.1 | 親子関係をドキュメントのパスで表すと、付け替えのたびにドキュメントの作り直しになる |
| 配下全体に及ぶ操作（削除・達成・取り消し）を、オフラインでも一括で反映する | 6.3.2〜6.3.4、6.3.7、NFR-007 | 配下の項目がローカルキャッシュにある必要がある。オフラインで失敗するトランザクションは使えない |
| 画面はツリー全体か、そこから絞り込んだもの | 7章 | 画面ごとのクエリより、全体を読み込んで手元で組み立てるほうが単純 |
| 並び順のルールが複雑 | 7.3 | Firestore の `orderBy` では表せないので、並べ替えはクライアントで行う |

### 規模の見積り

1日に10件のタスクを作るとして、1年で目的20件・目標200件・タスク3,600件ほど。済みの項目も削除しない限り残るので、データ量は単調に増える。

## 3. コレクション設計

### 3.1 構造

```
users/{uid}                      … ドキュメント本体は作らない（パスの区切りとしてのみ使う）
 ├─ purposes/{purposeId}         … 目的
 ├─ goals/{goalId}               … 目標（purposeId で親を参照）
 └─ tasks/{taskId}               … タスク（goalId で親を参照）
```

- ユーザーごとのサブコレクションに、目的・目標・タスクの3つを**同じ階層に並べる**。親子関係はパスではなく、親の ID を持つフィールドで表す
- ドキュメント ID は Firestore の自動 ID（`collection.doc()`）。クライアントで ID を決めるので、オフラインでも作成できる
- ID はドキュメント ID だけで持ち、フィールドには重複して持たない

### 3.2 この構造にする理由

| 判断 | 理由 |
|------|------|
| ユーザーごとのサブコレクションにする | セキュリティルールがパスだけで「本人のデータか」を判定できる。クエリに `where('userId', ...)` を付け忘れて全体が拒否される事故（ルールはフィルタではない）が起きない |
| 目標・タスクを親の下にネストしない | 親の付け替え（6.3.1）が `purposeId` / `goalId` の1フィールドの更新で済む。ネストすると付け替えのたびに配下ごと別パスへ作り直しになり、ID も変わる |
| 3種類を別コレクションにする | 項目ごとにフィールドと状態の値が違う。1つのコレクションに `type` で混ぜると、ルールでの検証とモデルの型付けが複雑になる |

### 3.3 ドキュメントのスキーマ

すべてのフィールドを常に書き込む。値がない任意項目は、フィールドを省かず `null` を入れる（フィールドの有無と `null` の2通りの「空」を作らない）。

#### purposes/{purposeId}

| フィールド | 型 | 必須 | 説明 |
|-----------|----|------|------|
| `name` | string | Yes | 空白のみは不可。100文字以内 |
| `description` | string \| null | Yes | 説明文。2,000文字以内 |
| `status` | string | Yes | `unachieved` / `achieved` |
| `createdAt` | timestamp | Yes | 作成日時（サーバー時刻）。作成後は変更しない |

#### goals/{goalId}

| フィールド | 型 | 必須 | 説明 |
|-----------|----|------|------|
| `purposeId` | string | Yes | 親の目的のドキュメント ID |
| `name` | string | Yes | 空白のみは不可。100文字以内 |
| `description` | string \| null | Yes | 説明文。2,000文字以内 |
| `dueDate` | string | Yes | 期日。`YYYY-MM-DD` |
| `achievementCriteria` | string | Yes | 達成基準。空白のみは不可。2,000文字以内 |
| `status` | string | Yes | `unachieved` / `achieved` / `achieved_by_parent` |
| `createdAt` | timestamp | Yes | 作成日時（サーバー時刻）。作成後は変更しない |

目標は「何を（名前）、いつまでに（期日）、どの程度（達成基準）」の3要素で成り立つので、期日と達成基準も必須とする（REQ-001 6.2）。

#### tasks/{taskId}

| フィールド | 型 | 必須 | 説明 |
|-----------|----|------|------|
| `goalId` | string | Yes | 親の目標のドキュメント ID |
| `name` | string | Yes | 空白のみは不可。100文字以内 |
| `scheduledDate` | string \| null | Yes | 予定日。`YYYY-MM-DD` |
| `important` | bool | Yes | 重要 |
| `urgent` | bool | Yes | 緊急 |
| `status` | string | Yes | `incomplete` / `complete` / `complete_by_parent` |
| `createdAt` | timestamp | Yes | 作成日時（サーバー時刻）。作成後は変更しない |

### 3.4 型の決め方

| 項目 | 決定 | 理由 |
|------|------|------|
| 期日・予定日 | `YYYY-MM-DD` の文字列 | 時刻を持たない「暦の日付」なので。timestamp にするとタイムゾーンの解釈で日付がずれうる。文字列は辞書順が日付順になり、今日との比較（期限切れの判定、NFR-006）も文字列比較で済む |
| 作成日時 | サーバー時刻（`FieldValue.serverTimestamp()`） | 端末の時計に左右されない。オフラインで作った項目は「同期した時刻」になるが、許容する |
| 親の参照 | ドキュメント ID の文字列 | 3.5 のとおり |
| 状態 | 要件の値をそのまま文字列で持つ | 「親の達成で済み」は達成の取り消し（6.3.4）に必要なので、表示が同じでも区別して保存する |
| 更新日時 | 持たない | 要件で使わない |
| 文字数の上限 | 名前は100文字、説明文・達成基準は2,000文字（REQ-001 6.2、7.4） | 上限はアプリの入力欄（`TextField` の `maxLength`）で守る。ルールには、壊れたデータを防ぐための緩い上限（4倍）だけを置く（5.1） |

#### サーバー時刻の扱い

作成直後、サーバーに届くまでの間は、`createdAt` がリスナーから `null` で返ってくる。Web 版の cloud_firestore（7.1.0）はリスナー（`snapshots()`）で `ServerTimestampBehavior` を指定できず、推定値（`estimate`）を受け取れないため。

- モデルでは `createdAt` を `DateTime?` とし、`null` は「同期待ち」を表す
- 並べ替え（7.3）では、`null` を最も新しいものとして扱う（作ったばかりの項目なので、実際にも最も新しい）

### 3.5 親の参照: ID の文字列か、DocumentReference か

Firestore には、ほかのドキュメントを指す参照型（`DocumentReference`）がある。親の参照に文字列と参照型のどちらを使うかを比べる。

| 観点 | ID の文字列（`purposeId: "abc"`） | 参照型（`purposeRef: users/u1/purposes/abc`） |
|------|----------------------------------|----------------------------------------------|
| 他人のデータを指せないか | パスの組み立てはルールとアプリ側で `users/{uid}` を使うので、構造上ほかのユーザーのドキュメントを指せない | 任意のパスを保存できる。自分の `users/{uid}/purposes/...` を指していることを、ルールで追加で検証する必要がある |
| 構造の変更への強さ | ID だけなので、コレクションの位置を変えても値は変わらない | パス全体を持つので、構造を変えると全件の書き換えが要る |
| モデルとテスト | Dart の `String` で済み、ドメインのコードが Firestore に依存しない。テストのデータも作りやすい | モデルが `cloud_firestore` の型に依存する。テストでは参照を作るためにFirestore のインスタンス（またはフェイク）が要る |
| 手元での組み立て | ID をキーにした `Map` でそのまま親子をつなげる | 参照から ID（`ref.id`）を取り出して使うことになり、結局は ID を使う |
| 便利な点 | とくになし | `ref.get()` で親をそのまま読める。コンソールで参照先へのリンクとして表示される。型として「参照」であることが明確 |
| サイズ | 小さい | パス全体を持つ分だけ大きい（この規模では無視できる） |

**決定**: ID の文字列にする。参照型の利点（親をその場で読む、コンソールでのリンク）は、全件を読み込んで手元で組み立てるこの設計（4.1）では活きない。一方で、ルールでの追加の検証や、モデルが Firestore に依存することが負担になる。

### 3.6 インデックス

- 複合インデックスは使わない（4.1 のとおり、クエリは条件なしでコレクション全体を読むだけ）
- 単一フィールドインデックスは既定のまま。検索に使わない長い文字列（`description`、`achievementCriteria`）は、ベストプラクティスに従ってインデックス対象から外す（[firestore.indexes.json](../../firestore.indexes.json) の `fieldOverrides`）

## 4. 読み取りと書き込み

### 4.1 読み取り

ログイン中は、3つのコレクションの**全体**をそれぞれリアルタイムリスナー（`snapshots()`）で購読し続ける。ツリーの組み立て、今日の画面の絞り込み、並べ替え、件数（「2/5」）の集計はすべてクライアントで行う。

| 理由 | 説明 |
|------|------|
| オフラインでの一括操作に必要 | 削除・達成・取り消しでは、済みの項目を含む配下全体をたどって書き換え先を決める（6.3.2〜6.3.4）。配下がローカルキャッシュにないと、オフラインでは正しく操作できない |
| 画面の要件を満たすのに全件が要る | 「すべて」の画面は済みでない目標にも「完了したタスク数 / 全タスク数」を出すので、済みのタスクも要る。目的・目標は全件表示する |
| 集計値を持たずに済む | 件数を目標ドキュメントに持たせる（非正規化する）と、タスクに関わるすべての操作で更新が必要になり、ずれが生じやすい |

読み取りの課金は、リスナーを張るたびに件数分かかる。見積りの1年後（約3,800件）でも1回あたり数千件で、無料枠（1日5万件）と料金を考えれば問題にならない。タスクが1万件を超えるなど、読み込みの遅さや料金が目に見えてきたら見直す（8章）。

### 4.2 書き込み

複数のドキュメントを書き換える操作は、すべて `WriteBatch` で1回にまとめてコミットする（6.3.7）。トランザクションはオフラインで失敗するので使わない。書き換え先は、4.1 のリスナーで手元にあるデータから決める。

| 操作 | バッチの中身 |
|------|-------------|
| 作成 | 新しいドキュメント1件の `set`。`createdAt` は `FieldValue.serverTimestamp()` |
| 編集・親の付け替え・タスクの完了切り替え | 対象1件の `update`（変更するフィールドだけを送り、`createdAt` は送らない） |
| 削除（6.3.2） | 対象と、配下のすべてのドキュメントの `delete` |
| 達成（6.3.3） | 対象を `achieved` にし、配下の未済みの項目を「親の達成で済み」にする `update` |
| 達成の取り消し（6.3.4） | 対象を `unachieved` にし、「親の達成で済み」の子を未済みに戻す `update`（その子の配下も同様にたどる） |

- 更新で `createdAt` を送らないのは、同期待ちで手元の値が `null` の項目を編集したときに、`null` で上書きしないため
- Firestore はドキュメントを削除してもサブコレクションを消さないが、この設計では親子をパスでつないでいないので、配下は上の表のとおりバッチで明示的に削除する

## 5. セキュリティルール

### 5.1 方針

| 検証すること | 方法 |
|-------------|------|
| 本人のデータだけを読み書きできる（NFR-004） | パスの `{uid}` とログイン中のユーザーの UID が一致すること |
| ドキュメントの形が正しい | フィールドの過不足・型・状態の値・日付の形式・必須の文字列が空でないこと |
| 文字列が極端に長くない | 名前は400、説明文・達成基準は8,000（`size()`）まで。アプリの上限（100 / 2,000文字）の4倍にしているのは、ルールの `size()` が何を1文字と数えるか公式に明記されておらず、入力欄の数え方（見た目の1文字）と絵文字などで食い違いうるため |
| 作成日時が正しい | 作成時は `createdAt` がサーバー時刻（`request.time`）と一致し、更新時は変わっていないこと |
| 親がいない項目や、済みの親の下に未済みの項目を作れない（原理1、6.3.1） | 作成時と親の付け替え時に、親が存在し、未済みであること（`getAfter()`） |

不変条件（I1, I2）や配下への連動のすべてはルールでは検証せず、アプリ側で守る。すべてを検証しようとすると、`get()` 系の呼び出し回数の上限（1リクエストあたり10回、バッチ全体で20回）に当たる。利用者は自分1人なので、ルールで守るのは「他人のデータに触れない」ことと「明らかに壊れたデータを作らない」ことにとどめる。

### 5.2 ルール案

```
rules_version = '2';

service cloud.firestore {
  match /databases/{database}/documents {
    match /users/{uid} {
      function isOwner() {
        return request.auth != null && request.auth.uid == uid;
      }

      function docPath(collection, id) {
        return /databases/$(database)/documents/users/$(uid)/$(collection)/$(id);
      }

      // 名前: 空白のみは不可。上限はアプリ（100文字）の4倍の緩い値
      function isName(v) {
        return v is string && v.trim().size() > 0 && v.size() <= 400;
      }

      // 説明文・達成基準: 上限はアプリ（2,000文字）の4倍の緩い値
      function isLongText(v) {
        return v is string && v.trim().size() > 0 && v.size() <= 8000;
      }

      function isOptLongText(v) {
        return v == null || (v is string && v.size() <= 8000);
      }

      function isDate(v) {
        return v is string && v.matches('^[0-9]{4}-[0-9]{2}-[0-9]{2}$');
      }

      function isOptDate(v) {
        return v == null || isDate(v);
      }

      // 作成時はサーバー時刻、更新時は元の値のまま
      function hasValidCreatedAt() {
        return (resource == null && request.resource.data.createdAt == request.time)
          || (resource != null && request.resource.data.createdAt == resource.data.createdAt);
      }

      // 作成時、または親の ID が変わったときだけ親を確認する（get 系の呼び出しを最小にする）
      function parentChanged(field) {
        return resource == null || request.resource.data[field] != resource.data[field];
      }

      // 親が存在しなければ getAfter() は null を返す
      function isOpenParent(parent, openStatus) {
        return parent != null && parent.data.status == openStatus;
      }

      match /purposes/{purposeId} {
        function isValid(d) {
          return d.keys().hasOnly(['name', 'description', 'status', 'createdAt'])
            && d.keys().hasAll(['name', 'description', 'status', 'createdAt'])
            && isName(d.name)
            && isOptLongText(d.description)
            && d.status in ['unachieved', 'achieved'];
        }

        allow read, delete: if isOwner();
        allow create, update: if isOwner() && isValid(request.resource.data) && hasValidCreatedAt();
      }

      match /goals/{goalId} {
        function isValid(d) {
          return d.keys().hasOnly(['purposeId', 'name', 'description', 'dueDate', 'achievementCriteria', 'status', 'createdAt'])
            && d.keys().hasAll(['purposeId', 'name', 'description', 'dueDate', 'achievementCriteria', 'status', 'createdAt'])
            && d.purposeId is string
            && isName(d.name)
            && isOptLongText(d.description)
            && isDate(d.dueDate)
            && isLongText(d.achievementCriteria)
            && d.status in ['unachieved', 'achieved', 'achieved_by_parent'];
        }

        function hasOpenParent(d) {
          return !parentChanged('purposeId')
            || isOpenParent(getAfter(docPath('purposes', d.purposeId)), 'unachieved');
        }

        allow read, delete: if isOwner();
        allow create, update: if isOwner() && isValid(request.resource.data) && hasValidCreatedAt()
          && hasOpenParent(request.resource.data);
      }

      match /tasks/{taskId} {
        function isValid(d) {
          return d.keys().hasOnly(['goalId', 'name', 'scheduledDate', 'important', 'urgent', 'status', 'createdAt'])
            && d.keys().hasAll(['goalId', 'name', 'scheduledDate', 'important', 'urgent', 'status', 'createdAt'])
            && d.goalId is string
            && isName(d.name)
            && isOptDate(d.scheduledDate)
            && d.important is bool
            && d.urgent is bool
            && d.status in ['incomplete', 'complete', 'complete_by_parent'];
        }

        function hasOpenParent(d) {
          return !parentChanged('goalId')
            || isOpenParent(getAfter(docPath('goals', d.goalId)), 'unachieved');
        }

        allow read, delete: if isOwner();
        allow create, update: if isOwner() && isValid(request.resource.data) && hasValidCreatedAt()
          && hasOpenParent(request.resource.data);
      }
    }
  }
}
```

ルールは Firestore Emulator 上のテスト（`@firebase/rules-unit-testing`）で検証してからデプロイする。

## 6. アプリ構成

### 6.1 モデル（freezed）

目的・目標・タスクを freezed のイミュータブルなクラスで表す。Firestore のドキュメントとの変換は手書きにする（6.2）。json_serializable は使わない。

### 6.2 Firestore との変換: 手書きか、json_serializable か

| 観点 | 手書き | json_serializable |
|------|--------|-------------------|
| 書く量 | 1モデルあたり、読み取り（`fromFirestore`）と書き込み（作成用・更新用）の関数を書く。3モデル × 7フィールド程度 | `fromJson` / `toJson` が生成される。変換器（`JsonConverter`）とアノテーションを書く |
| ドキュメント ID | `doc.id` をそのまま渡せる | ID はドキュメントのデータに含まれないので、読むときに `{...doc.data(), 'id': doc.id}` のように混ぜ、書くときは `@JsonKey(includeToJson: false)` で外す |
| `Timestamp` | その場で `DateTime` に変換する | `Timestamp` と `DateTime` の変換器を書く（json_serializable の対応型に Firestore の型は含まれない） |
| サーバー時刻 | 作成用の関数で `FieldValue.serverTimestamp()` を入れる | `toJson` は `DateTime` を書き出すので、作成時だけ `createdAt` を差し替える処理が別途要る |
| 作成と更新で中身が違う | 作成用（全フィールド＋サーバー時刻）と更新用（変更分のみ）を分けて書ける | `toJson` は1種類なので、更新用の Map は結局手で組み立てる |
| フィールド名の打ち間違い | 起こりうる。変換のテストで防ぐ | 生成されるので起こらない |
| コード生成 | freezed の分だけ | freezed に加えて json_serializable の分（`.g.dart`）も生成する |

**決定**: 手書き。この設計では、ID をデータの外に持つこと、サーバー時刻、作成と更新で送る中身が違うことなど、Firestore 特有の差分が多い。json_serializable を使っても、その差分は結局手で書くことになる。フィールド名の打ち間違いは、変換の単体テストで防ぐ。

### 6.3 状態管理（Riverpod）

プロバイダはコード生成（`@riverpod` と riverpod_generator）で定義する。freezed のために build_runner を使うので、公式ドキュメントの目安（ほかの用途でコード生成を使っているなら使う）に合う。コード生成で定義したプロバイダは、既定で使われなくなると破棄される（autoDispose）。

| プロバイダ | 中身 |
|-----------|------|
| 認証状態 | `FirebaseAuth.authStateChanges()` を流す |
| 目的・目標・タスクの一覧 | ログイン中のユーザーの各コレクションを `snapshots()` で流す（4.1）。ログアウトで破棄される |
| ツリー | 3つの一覧から組み立てた、親子関係と状態を持つ読み取り専用のモデル |
| 今日 | ツリーと今日の日付から、今日の画面に出す範囲を絞り込んだもの。日付が変わったら作り直す（NFR-006） |
| 操作 | 作成・編集・削除・達成・取り消し・完了切り替え。ツリーから書き換え先を決めて、`WriteBatch` を作ってコミットする |

連動のルール（6.3）とバッチの組み立ては、Firestore に依存しない純粋な Dart のコードに分け、単体テストで検証する。

### 6.4 ルーティング（go_router）

| パス | 画面 | 認証 |
|------|------|------|
| `/login` | ログイン | 不要 |
| `/today` | 今日（ログイン後の最初の画面） | 必要 |
| `/all` | すべて | 必要 |

- 未ログインで認証が必要な画面を開くと `/login` へ、ログイン済みで `/login` を開くと `/today` へ移る（`redirect`）
- 認証状態が変わったら、`redirect` を評価し直す（`refreshListenable`）

## 7. 検討して採用しなかった案

| 案 | 採用しない理由 |
|----|---------------|
| ユーザーごとに1ドキュメントへツリー全体を入れる | ドキュメントの上限（1 MiB）に向かって育ち続ける。小さな変更でも毎回ドキュメント全体を書き換えることになり、複数タブやオフラインからの書き込みが競合しやすい |
| `purposes/{id}/goals/{id}/tasks/{id}` とネストする | 親の付け替えのたびに、配下ごと別パスへの作り直しが必要になる。ID も変わる |
| ルートの `purposes` などに `userId` フィールドを持たせる | すべてのクエリに `where('userId', ...)` が必要になり、付け忘れるとルールでクエリ全体が拒否される。ルールも書きにくくなる |
| タスクに `purposeId` も持たせる | 目標の付け替えのたびに、配下のタスクすべての書き換えが必要になる。目的は目標から引けば足りる |
| 目標に完了タスク数などの集計値を持たせる | 4.1 のとおり。全件を読み込むので必要ない |
| 親の参照に `DocumentReference` を使う | 3.5 のとおり |
| 一括の操作にトランザクションを使う | オフラインで失敗するので、NFR-007 と 6.3.7 を満たせない |

## 8. リスクと今後の課題

| リスク | 対応 |
|--------|------|
| 済みの項目が増え続け、毎回の読み込み量が増える | 見積り上、当面は問題ない。タスクが1万件を超えるなどして読み込みの遅さが目に見えたら、済みの項目を別コレクションへ移す、読み込み範囲を絞るなどを検討する |
| 複数のタブや端末から同時に操作すると、連動の結果が食い違うことがある | 同時にツリーを操作するのは本人だけで、起きにくい。Web の永続キャッシュは複数タブで同期する（`WebPersistentMultipleTabManager`） |
| オフラインで作った項目の作成日時が同期した時刻になり、並び順が作った順とずれる | 許容する（3.4） |
