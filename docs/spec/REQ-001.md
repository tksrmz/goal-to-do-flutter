# Goal to Do MVP 要件定義書（Flutter + Firebase 版）

- 作成日: 2026-11-06
- 前身: [goal-to-do アルファ版 要件定義書（Vue + Supabase）](https://github.com/tksrmz/goal-to-do/blob/main/docs/spec/REQ-001.md)
- ステータス: ドラフト

## 1. 背景・課題

一般的なToDoアプリは日々のタスク管理には向いているが、「なぜそれをやるのか（目的）」や「何を達成したいのか（目標）」との紐付けが難しい。一方、長期目標まで管理しようとすると、エンタープライズ向けツールやNotionでの複雑な設定が必要になる。

アルファ版（Vue + Supabase）でこのコンセプトを検証したが、多対多のリンク、層ごとに異なる存在条件、アーカイブと目標ステータスの併存などにより、ルールが複雑で分かりにくかった。本MVPでは Flutter + Firebase で作り直すにあたり、世界モデルを単純化したうえで、コンセプトの核である「目的を定めたうえで行動する」をより強く打ち出す。

## 2. 対象ユーザー

開発者本人（シングルユーザー）。日々のタスクを長期的な目的・目標と紐付けて管理したい。Webブラウザからアクセスして利用する。

## 3. ゴール（成功条件）

- [ ] Flutter Web アプリとして公開され、ブラウザからいつでもアクセスできる
- [ ] 管理者が Firebase コンソールで作成したアカウントでのみログインでき、自分のデータだけにアクセスできる
- [ ] 目的の作成からタスクの完了、目標・目的の達成、達成の取り消しまでの主要ワークフローがエラーなく完了する
- [ ] 操作結果が永続化され、リロードやセッションをまたいでもデータが失われない
- [ ] 自分で日常的に使い、使い勝手を検証できる

## 4. Non-goals（やらないこと）

- モバイルネイティブアプリ（Webのみ）
- マルチユーザー・チーム機能
- アプリからの新規アカウント登録
- 繰り返しタスク
- 目標タイムライン（ガントチャート）
- アイゼンハワーマトリクスの4象限表示（重要・緊急フラグはタグ表示と並び順にのみ使う）
- 「達成していないが、もう追わない」状態（中止など）。やめたものは削除で対応する
- 親を持たない目標・タスク
- 複数の親を持つ目標・タスク（多対多のリンク）
- 目的・目標の手動並べ替え
- アルファ版（Supabase）からのデータ移行

## 5. 用語定義

| 用語 | 定義 |
|------|------|
| 目的（Purpose） | 「〇〇のために」という形式で表される、活動の理由・意義。期日や達成基準を持たない |
| 目標（Goal） | SMARTな目標。具体的で測定可能で、期日と達成基準を持つ |
| タスク（Task） | 数時間で実行可能な作業単位。明確な完了基準を持つ |
| 親 / 子 | 目的は目標の親、目標はタスクの親。子から見た上位の項目が親 |
| 配下 | ある項目の子と、子の子（孫）の総称 |
| 済み | 目的・目標の「達成」「親の達成で達成」、タスクの「完了」「親の達成で完了」の総称 |
| 未済み | 目的・目標の「未達成」、タスクの「未完了」 |
| 期限切れ | 予定日が今日より前で、未完了のタスク |
| 今日 | 端末のタイムゾーンにおける現在の日付 |

## 6. 世界モデル

### 6.1 設計原理

#### 原理1: ツリー構造

世界モデルは目的・目標・タスクの3層のツリーで構成される。

```
目的 (Purpose)
 └─ 目標 (Goal)      … 必ず1つの目的に属する
     └─ タスク (Task) … 必ず1つの目標に属する
```

- 目的はツリーの根であり、親を持たない
- 目標とタスクは必ずちょうど1つの親を持つ。親のない目標・タスクは存在しない

#### 原理2: 終わり方は「済み」の1種類で、配下にも及ぶ

各項目の終わりは「済み」の1種類のみとする（目的・目標は達成、タスクは完了）。親が済みになると、配下もすべて済みになる。済みを取り消すと、配下は済みになる前の状態に戻る。

#### 原理3: 表示は状態から導出する

表示・非表示の状態はデータとして保存しない。済みかどうかによって、画面側で表示を決める。

### 6.2 データ

各データはログインユーザーに属し、本人以外は読み書きできない。物理的な保存構造（Firestore のコレクション設計など）は設計書で定める。

#### 目的（Purpose）

| 項目 | 必須 | 説明 |
|------|------|------|
| ID | Yes | 一意識別子 |
| 名前 | Yes | 「〇〇のために」の形式で管理される。空文字不可。100文字以内 |
| 説明文 | No | 目的の詳細な説明。2,000文字以内 |
| 状態 | Yes | `unachieved`（未達成）/ `achieved`（達成）。デフォルト: `unachieved` |
| 作成日時 | Yes | 並び順に使用 |

目的は親を持たないため、「親の達成で達成」の状態は存在しない。

#### 目標（Goal）

| 項目 | 必須 | 説明 |
|------|------|------|
| ID | Yes | 一意識別子 |
| 親の目的 | Yes | 目的のID。ちょうど1つ |
| 名前 | Yes | 空文字不可。100文字以内 |
| 説明文 | No | 目標の詳細な説明。2,000文字以内 |
| 期日 | Yes | 目標の達成期限（日付） |
| 達成基準 | Yes | フリーテキスト。空文字不可。2,000文字以内 |
| 状態 | Yes | `unachieved`（未達成）/ `achieved`（達成）/ `achieved_by_parent`（親の達成で達成）。デフォルト: `unachieved` |
| 作成日時 | Yes | 並び順に使用 |

#### タスク（Task）

| 項目 | 必須 | 説明 |
|------|------|------|
| ID | Yes | 一意識別子 |
| 親の目標 | Yes | 目標のID。ちょうど1つ |
| 名前 | Yes | 空文字不可。100文字以内 |
| 予定日 | No | タスクを実行する予定の日 |
| 重要 | Yes | 真偽値。デフォルト: false |
| 緊急 | Yes | 真偽値。デフォルト: false |
| 状態 | Yes | `incomplete`（未完了）/ `complete`（完了）/ `complete_by_parent`（親の達成で完了）。デフォルト: `incomplete` |
| 作成日時 | Yes | 並び順に使用 |

#### 状態の表示

`achieved` と `achieved_by_parent` は、画面上ではどちらも「達成」と表示する。`complete` と `complete_by_parent` は、どちらも「完了」と表示する。区別は「達成の取り消し」（6.3.4）でのみ使う。

### 6.3 操作ルール

#### 6.3.1 親の選択

- 目標の作成時に、親の目的をちょうど1つ選ぶ。タスクの作成時に、親の目標をちょうど1つ選ぶ（原理1）
- 編集時に親を別の項目へ付け替えられる。親を外す（親なしにする）ことはできない（原理1）
- 新しい親として選べるのは未済みの項目のみ（原理2: 済みの親の下に未済みの子を作らない）

#### 6.3.2 削除

項目を削除すると、その配下もすべて削除する。削除前に確認ダイアログを表示し、一緒に削除される配下の件数を示す。

```
目的P を削除
 └─ P、P の配下の全目標、それらの配下の全タスクを削除

目標G を削除
 └─ G、G の配下の全タスクを削除

タスクT を削除
 └─ T のみ削除
```

#### 6.3.3 達成（目的・目標）

項目Xを達成にすると、以下を行う（原理2）。

```
X を達成にする
 ├─ X の状態を achieved にする
 └─ X の配下の各項目C について:
     ├─ C が未済み → 親の達成で済み（achieved_by_parent / complete_by_parent）にする
     └─ C が済み   → 変更しない
```

配下に未済みの項目がある場合は、達成の前に確認ダイアログを表示し、一緒に済みになる件数を示す。

#### 6.3.4 達成の取り消し（目的・目標）

状態が `achieved` の項目Xの達成を取り消すと、配下を達成前の状態に戻す（原理2）。

```
X の達成を取り消す
 ├─ X の状態を unachieved にする
 └─ X の各子C について:
     ├─ C が親の達成で済み → C を未済み（unachieved / incomplete）に戻し、C の子にも同じ処理を行う
     └─ C が自分で済み（achieved / complete） → 変更しない（C の配下もたどらない）
```

例: 目的P の配下に、目標G1（達成）と目標G2（未達成）がある。G2 の配下に、タスクT1（完了）とタスクT2（未完了）がある。

| 操作 | G1 | G2 | T1 | T2 |
|------|----|----|----|----|
| P を達成 | achieved（変更なし） | achieved_by_parent | complete（変更なし） | complete_by_parent |
| P の達成を取り消す | achieved | unachieved | complete | incomplete |

#### 6.3.5 タスクの完了

- 未完了のタスクを完了（`complete`）にできる。完了のタスクを未完了（`incomplete`）に戻せる
- タスクの完了は親や兄弟に波及しない

#### 6.3.6 済みの親の配下は読み取り専用

親が済みである項目は、編集・削除・状態の変更・子の追加・親の付け替えができない。これにより、「親の達成で済み」の項目が単独で変更されることはない。変更したい場合は、先に親の達成を取り消す。

#### 6.3.7 複数項目の操作は一括で反映する

削除（6.3.2）、達成（6.3.3）、達成の取り消し（6.3.4）のように複数の項目を書き換える操作は、すべての書き換えが反映されるか、何も反映されないかのどちらかとする。一部だけが反映された状態にはならない。オフライン中の操作も同様とする。

#### 6.3.8 不変条件

上記のルールにより、以下が常に成り立つ。

- **I1**: 済みの項目の配下に、未済みの項目は存在しない
- **I2**: 「親の達成で済み」の項目の親は、必ず済みである

I1 より、未済みの項目の祖先はすべて未済みである。

### 6.4 達成の提案

ユーザーの操作をきっかけに、上位の項目の達成を提案する。

```
タスクを完了にする（ユーザー操作）
 └─ 親の目標の配下タスクがすべて完了した？
     ├─ Yes ──> 「目標「〇〇」に紐付くすべてのタスクが完了しました。この目標を達成にしますか？」
     │          ├─ 達成にする ──> 目標を achieved にする ──> ※下記へ
     │          └─ 後で ──> 変更なし
     └─ No ──> 終了

目標を達成にする（ユーザー操作、または上記の提案の受諾）
 └─ 親の目的の配下目標がすべて達成した？
     ├─ Yes ──> 「目的「〇〇」に紐付くすべての目標が達成されました。この目的を達成にしますか？」
     │          ├─ 達成にする ──> 目的を achieved にする
     │          └─ 後で ──> 変更なし
     └─ No ──> 終了
```

- 提案を受諾した結果の達成は、ユーザーが自分で達成したもの（`achieved`）として扱う
- 複数の提案が該当する場合は、順に表示する

## 7. 画面

| 画面 | 認証 | 概要 |
|------|------|------|
| ログイン | 不要 | メールアドレスとパスワードでログインする |
| 今日 | 必要 | 今日やるべきタスクを、目的・目標のまとまりで表示する。ログイン後の最初の画面 |
| すべて | 必要 | 全項目をツリーで表示し、作成・編集・削除・達成を行う |

認証が必要な画面には、今日・すべてへのナビゲーションとログアウト操作を置く。

### 7.1 今日

```
■ 転職するために                          ← 目的（見出し）
   ▸ 3月までに内定を1社得る               ← 目標（小見出し）
      [ ] 職務経歴書を直す   重要 緊急  11/04  ← 期限切れ（日付を赤で強調）
      [ ] エージェントに返信  重要       11/06
■ 生活を回すために
   ▸ 日常
      [ ] ゴミ出し                      11/06
```

- 表示するのは、予定日が今日以前の未完了タスクと、その親の目標・祖先の目的のみ。表示対象のタスクを持たない目標・目的は表示しない
- 開閉（アコーディオン）はなく、常にすべて表示する
- 各タスクに、チェックボックス・名前・重要タグ・緊急タグ・予定日を表示する
- この画面で行える操作は、タスクの完了切り替えとタスクの新規作成のみ
- 完了にしたタスクはすぐには消さず、打ち消し線で表示したまま残す。画面を開き直すと表示されなくなる
- 新規タスク作成では、予定日の初期値を今日とする。親の目標の選択は必須

### 7.2 すべて

```
[+ 新規目的]                                      [ ] 済みも表示
▼ 転職するために                    [+目標] [編集] [削除] [達成]
   ▼ 3月までに内定を1社得る  期日 3/31  2/5    [+タスク] [編集] [削除] [達成]
        [ ] 職務経歴書を直す   重要 緊急  11/04         [編集] [削除]
        [x] 求人を5社分リストアップ                     [編集] [削除]
   ▼ ポートフォリオを公開する  0/3               [+タスク] [編集] [削除] [達成]
        [ ] 作品を3つ選ぶ          重要       11/10         [編集] [削除]
▼ 生活を回すために                  [+目標] [編集] [削除] [達成]
   ▼ 日常  0/1                                   [+タスク] [編集] [削除] [達成]
        [ ] ゴミ出し                          11/06         [編集] [削除]
```

- 目的と目標の2段のアコーディオンで表示する。目的を開くと配下の目標、目標を開くと配下のタスクが表示される
- 画面を表示したときは、すべての目的・目標が開いた状態とする。開閉の状態は保存せず、画面を開き直すとすべて開いた状態に戻る。画面を開いている間に追加した目的・目標も、開いた状態で表示する
- 目標の行には、期日と「完了したタスク数 / 全タスク数」を表示する。完了したタスク数には「親の達成で完了」も含む
- 目標を開いたときに、達成基準を表示する
- 「済みも表示」は初期状態 OFF。OFF のときは済みの項目を表示しない。ON のときは済みの項目も表示する
- 操作中に済みにした項目は、今日の画面と同様に、画面を開き直すまで済みの表示で残す
- 各行の操作は以下のとおり。済みの親の配下にある項目では、これらの操作を行えない（6.3.6）

| 対象 | 操作 |
|------|------|
| 目的 | 目標の追加、編集、削除、達成 / 達成の取り消し |
| 目標 | タスクの追加、編集（親の付け替えを含む）、削除、達成 / 達成の取り消し |
| タスク | 完了の切り替え、編集（親の付け替えを含む）、削除 |

### 7.3 並び順

#### タスク

親の目標ごとのタスク一覧の中で、以下の順に並べる。今日・すべての両画面に適用する。

1. 期限切れ
2. 重要かつ緊急
3. 重要のみ
4. 緊急のみ
5. 重要でも緊急でもない

同じ区分の中では予定日の古い順（予定日のないものは予定日のあるものの後）、それも同じなら作成日時の古い順とする。期限切れのタスク同士は、2〜5 の区分、予定日、作成日時の順で並べる。

すべての画面で「済みも表示」が ON のとき、済みのタスクは目標ごとのタスク一覧の末尾にまとめ、その中は上記と同じ順で並べる。

#### 目的・目標

作成日時の古い順とする。

### 7.4 入力フォーム

| フォーム | 項目 | バリデーション |
|---------|------|-------------|
| 目的 | 名前、説明文 | 名前は必須（「名前を入力してください」） |
| 目標 | 名前、説明文、期日、達成基準、親の目的 | 名前は必須。期日は必須（「期日を入力してください」）。達成基準は必須（「達成基準を入力してください」）。親の目的は必須（「目的を選択してください」）。選択肢は未達成の目的のみ |
| タスク | 名前、予定日、重要、緊急、親の目標 | 名前は必須。親の目標は必須（「目標を選択してください」）。選択肢は未達成の目標のみ。予定日は空にして解除できる |

名前は100文字以内、説明文・達成基準は2,000文字以内とする。入力欄に入力中の文字数と上限を表示し、上限を超えて入力できないようにする。

いずれのフォームも、キャンセルすると変更を破棄して閉じる。

## 8. 機能要件（FR）

- **FR-001**: As a ユーザー, I want to 管理者が作成したアカウントのメールアドレスとパスワードでログイン・ログアウトする, so that 自分だけがデータにアクセスできる
- **FR-002**: As a ユーザー, I want to アプリを開いたときに今日やるべきタスク（予定日が今日のもの＋期限切れ）を目的・目標のまとまりで見る, so that 今日何をすべきか、なぜそれをやるのかを即座に把握できる
- **FR-003**: As a ユーザー, I want to 目的を作成・編集・削除する, so that 活動の理由を明文化して管理できる
- **FR-004**: As a ユーザー, I want to 目的に属する目標を作成・編集・削除し、別の目的へ付け替える, so that 達成したいゴールを具体的に定義できる
- **FR-005**: As a ユーザー, I want to 目標に属するタスクを作成・編集・削除し、別の目標へ付け替え、予定日・重要・緊急を設定する, so that 日々の作業を目的・目標と紐付けて管理できる
- **FR-006**: As a ユーザー, I want to タスクの完了・未完了を切り替える, so that 作業の進捗を記録できる
- **FR-007**: As a ユーザー, I want to 目的・目標を達成にし、必要なら達成を取り消す, so that 終わったものを配下ごと片付けつつ、誤操作しても元に戻せる
- **FR-008**: As a ユーザー, I want to タスクがすべて完了したときに目標の達成を、目標がすべて達成されたときに目的の達成を提案される, so that ボトムアップで達成を積み上げられる
- **FR-009**: As a ユーザー, I want to すべての項目をツリーで見て、済みの項目の表示を切り替える, so that 目的・目標・タスクの全体像を把握できる
- **FR-010**: As a ユーザー, I want to タスクが期限切れ・重要度・緊急度に基づく順で並ぶ, so that 優先すべきタスクを上から順に処理できる

## 9. 非機能要件（NFR）

### 性能

- **NFR-001**: 主要操作（タスクの完了切り替え、項目の作成・編集・削除、達成・取り消し）の結果が、操作後1秒以内に画面へ反映されること

### セキュリティ

- **NFR-002**: Firebase Authentication によるメールアドレス＋パスワード認証を必須とし、未ログインのユーザーはアプリの機能にアクセスできない
- **NFR-003**: エンドユーザーによるアカウント作成をプロジェクト設定で無効化し（Firebase コンソールの Authentication > Settings > User actions）、利用者を管理者が Firebase コンソールで作成したアカウントに限定する。アプリには新規登録の画面を設けない
- **NFR-004**: Firestore のセキュリティルールにより、ログインユーザーは自分のデータのみ参照・更新できる

### データ整合性

- **NFR-005**: 複数の項目を書き換える操作は一括で反映する（6.3.7）
- **NFR-006**: 日付（今日・期限切れ）の判定は端末のタイムゾーンで行う。アプリを開いたまま日付が変わった場合も、新しい日付で判定する

### オフライン

- **NFR-007**: Firestore のオフライン永続化を有効にする。アプリを開いている間にネットワークが切れても、閲覧と操作を続けられ、ネットワークの復帰時にサーバーと同期される
- **NFR-008**: 初回のログインにはネットワーク接続が必要とする

### 可用性

- **NFR-009**: Firebase のマネージドインフラに依存し、独自の可用性対策は行わない

## 10. 制約

- フロントエンド: Flutter（Web）
- バックエンド: Firebase（Authentication, Cloud Firestore）
- ホスティング: Firebase Hosting
- 対応ブラウザ: Chrome, Safari, Firefox の最新版（Firestore の Web 版オフライン永続化の対応ブラウザに合わせる）
- レスポンシブ対応を行い、スマートフォンのブラウザでも利用できること

- **When** ユーザー2 でログインする、またはユーザー2 の認証情報でユーザー1 のデータを直接読み書きしようとする
- **Then** ユーザー1 のデータは表示されず、読み書きも拒否される

#### AC-060: オフライン中も操作でき、復帰後に同期される

- **Given** ログインしてアプリを開いている
- **When** ネットワークを切断した状態でタスクを完了にし、その後ネットワークを復帰させる
- **Then** 切断中も操作結果が画面に反映される
- **And** 復帰後に別の端末でログインすると、タスクが完了になっている
